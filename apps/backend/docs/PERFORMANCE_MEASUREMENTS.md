# 성능 실측 기록

`PERFORMANCE_BOTTLENECKS.md`에서 코드 분석으로 짚은 병목을 Artillery로 실제 재현/측정한 API별 결과.
측정 방법론(환경, 프로토콜, 재현 명령)은 `PERFORMANCE_BASELINE.md` 참고 — 여기는 결과만 남긴다.

제목 규칙: `## {API} — {코드 수정 전/후, 수정했다면 무엇을 고쳤는지}` → 그 아래
`### [주 지표|보조 지표] {테스트 종류}: Baseline #N`. 목차만 봐도 어떤 API를, 어떤 코드 상태에서
쟀는지 알 수 있게 유지한다.

## GET /api/rooms — 코드 수정 전

`Makefile`을 `spring-boot:run`으로 고쳐서 `server.tomcat.threads.max=10` 등 실제 배포 설정이
그대로 적용된 상태(`PERFORMANCE_BOTTLENECKS.md` 1번 항목)에서 측정. 방 200개 × 참가자 5명 시드.

### [주 지표] 스파이크 테스트: Baseline #1

`get-rooms-spike.yml`: baseline 20s@2req/s → spike **10초 동안 2,500 VU** 유입(초당 250명 —
이전에 쓰던 "2초 안에 500명"과 유입률은 동일하게 유지하면서 규모만 5배로 키운 버전).

| 지표 | 값 |
|---|---|
| 총 요청(=생성된 VU, VU당 요청 1건) | 2,540건 |
| 완료(200 응답) | 244건 |
| **실패(`ERR_SOCKET_TIMEOUT`)** | **2,296건 (90.4%)** |
| p50 | 539.2ms (완료된 것만) |
| p95 | 3,464.1ms |
| p99 | 3,678.4ms |
| max | 4,367ms |

**해석**:
- 완료된 요청의 지연시간 자체는 짧다(큐가 짧으니 개별 요청은 빨리 처리된다) — 하지만 **애초에
  큐/커넥션 슬롯에 들어가지도 못하고 튕기는 요청이 훨씬 많다.** 스레드 풀이 작을수록 "느리게라도
  응답"보다 "아예 거부"가 지배적인 실패 양상이 된다.
- "생존"이 채점 기준이므로, 이 90.4%가 코드 수정 전 진짜 출발점이다.
- `server.tomcat.accept-count=10` + `max-connections=50`이 순간 유입 앞에서 압도적으로 작다는 게
  그대로 드러난다 — `PERFORMANCE_BOTTLENECKS.md` 1번 항목(스레드 풀)이 실측으로도 최우선 순위임이
  확인됐다. 스파이크 규모를 500 VU → 2,500 VU로 5배 키우니 실패율도 73.0% → 90.4%로 같이 나빠졌다
  — 규모가 커질수록 이 병목의 영향이 더 크게 드러난다.

### [보조 지표] 30 req/s 스무스 램프: Baseline #1

| 지표 | 값 |
|---|---|
| 총 요청 | 1,535건 |
| 완료 | 878건 |
| p50 | 1,107.9ms |
| p95 | 1,495.5ms |
| p99 | 1,790.4ms |
| max | 1,828ms |
| **실패(`ERR_SOCKET_TIMEOUT`)** | **657건 (42.8%)** |

**해석**: 이 프로파일은 원래 "에러도 큐잉도 없는 가벼운 부하"로 설계했는데, 실제 스레드 풀(10개)
기준으로는 30 req/s조차 42.8%가 타임아웃난다 — Little's Law로 보면 지연시간이 늘어날수록 동시성이
10을 훌쩍 넘는 피드백 루프가 걸린 것으로 보인다. **이 프로파일은 더 이상 "에러 없는 세부 튜닝
구간" 역할을 못 한다** — 다음 라운드에서는 훨씬 낮은 req/s(예: 5 이하)로 다시 잡아야 "요청 1건이
가벼워졌는가"를 순수하게 비교할 수 있다. (`get-rooms-baseline.yml`의 arrivalRate를 낮추는 작업 필요.)

## GET /api/rooms — 코드 수정 후 (N+1 제거 + {room,timestamp} 인덱스 추가)

`RoomService.getAllRooms`/`mapToRoomResponse`가 방마다 creator/participant를 개별 `findById`로,
최근 메시지 수를 개별 COUNT 쿼리로 조회하던 걸, `userRepository.findAllById`(유저 배치 조회)와
`MessageRepository.countRecentMessagesByRoomIds`(방 여러 개를 한 번에 `$group` 집계)로 바꿨다.
`Message`에 `{room, timestamp}` 복합 인덱스도 추가했다(`PERFORMANCE_BOTTLENECKS.md` 2번·3번 항목).

### [주 지표] 스파이크 테스트: Baseline #2

| 지표 | Baseline #1 (수정 전) | **Baseline #2 (N+1 제거 후)** |
|---|---|---|
| 총 요청 | 2,540건 | 2,540건 |
| 완료 | 244건 | 254건 |
| **실패(`ERR_SOCKET_TIMEOUT`)** | 2,296건 (90.4%) | **2,286건 (90.0%)** |
| p50(완료된 것만) | 539.2ms | **40.9ms** |
| p95 | 3,464.1ms | 3,828.5ms |
| p99 | 3,678.4ms | 3,905.8ms |
| max | 4,367ms | 3,913ms |

**해석**: 완료된 요청의 지연시간은 13배 빨라졌다(539ms → 41ms) — N+1 제거 자체는 확실히 효과가
있다. 하지만 **생존율(실패율)은 90.4% → 90.0%로 거의 그대로다.** 2,500명이 순간적으로 몰리면
`accept-count=10` + `max-connections=50`을 초과하는 연결은 애플리케이션 코드가 얼마나 빨라졌든
상관없이 **연결 단계에서부터** 거부/타임아웃되기 때문이다 — 요청이 아무리 가벼워져도 애초에
받아주질 못하면 소용없다. `PERFORMANCE_BOTTLENECKS.md` 1번 항목(스레드 풀/accept-count)이
이 정도 규모의 스파이크에서는 여전히 지배적인 병목임이 확인됐다.

### [보조 지표] 30 req/s 스무스 램프: Baseline #2

| 지표 | Baseline #1 (수정 전) | **Baseline #2 (N+1 제거 후)** |
|---|---|---|
| 총 요청 | 1,535건 | 1,535건 |
| 완료 | 878건 | 914건 |
| **실패(`ERR_SOCKET_TIMEOUT`)** | 657건 (42.8%) | **621건 (40.5%)** |
| p50 | 1,107.9ms | **854.2ms** |
| p95 | 1,495.5ms | 963.1ms |
| p99 | 1,790.4ms | 1,002.4ms |
| max | 1,828ms | 1,082ms |

**해석**: 여기서도 마찬가지로 지연시간은 개선(1,108ms → 854ms, p95/p99는 더 크게 개선)됐지만
실패율은 42.8% → 40.5%로 소폭만 줄었다. 30 req/s 정도로도 이미 스레드 풀(10개) 용량을 넘어서는
큐잉이 걸리기 때문에, N+1 제거만으로는 이 부하를 완전히 못 버틴다 — 스레드 풀/accept-count를
같이 늘려야 실패율이 눈에 띄게 줄어들 것으로 보인다.

## GET /api/rooms — 코드 수정 후 (+ 스레드 풀 확장: threads.max 10→100, accept-count 10→300, max-connections 50→1000)

`application.properties`: `server.tomcat.threads.max=100`, `threads.min-spare=5`,
`accept-count=300`, `max-connections=1000`으로 상향(`PERFORMANCE_BOTTLENECKS.md` 1번 항목).
N+1 제거(Baseline #2)는 이미 적용된 상태 위에 얹은 것 — 두 수정의 합산 효과.

### [주 지표] 스파이크 테스트: Baseline #3

| 지표 | Baseline #1 (수정 전) | Baseline #2 (N+1만) | **Baseline #3 (N+1 + 스레드 풀)** |
|---|---|---|---|
| 총 요청 | 2,540건 | 2,540건 | 2,540건 |
| 완료 | 244건 | 254건 | **2,540건** |
| **실패(`ERR_SOCKET_TIMEOUT`)** | 2,296건 (90.4%) | 2,286건 (90.0%) | **0건 (0%)** |
| p50 | 539.2ms | 40.9ms | **15ms** |
| p95 | 3,464.1ms | 3,828.5ms | **30.3ms** |
| p99 | 3,678.4ms | 3,905.8ms | **34.8ms** |
| max | 4,367ms | 3,913ms | **48ms** |

**해석**: 2,500명 스파이크를 **완전히 버텼다** — 실패 0건, p99 34.8ms. N+1만 고쳤을 때는 요청이
빨라져도 연결 자체가 거부돼서 생존율이 안 바뀌었는데(90.0%), 스레드 풀/accept-count/max-connections를
같이 올리니 "연결을 받아줄 슬롯"이 확보되면서 두 수정의 효과가 합쳐져 완전히 해소됐다. 순서가
중요했다 — 스레드 풀만 늘리고 N+1을 안 고쳤다면 느린 요청이 스레드 100개를 더 오래 붙잡아서
이만큼 좋아지지 않았을 것이다(정확히는 다음에 별도로 검증 필요).

### [보조 지표] 30 req/s 스무스 램프: Baseline #3

| 지표 | Baseline #1 (수정 전) | Baseline #2 (N+1만) | **Baseline #3 (N+1 + 스레드 풀)** |
|---|---|---|---|
| 총 요청 | 1,535건 | 1,535건 | 1,535건 |
| 완료 | 878건 | 914건 | **1,535건** |
| **실패(`ERR_SOCKET_TIMEOUT`)** | 657건 (42.8%) | 621건 (40.5%) | **0건 (0%)** |
| p50 | 1,107.9ms | 854.2ms | **10.9ms** |
| p95 | 1,495.5ms | 963.1ms | **16.9ms** |
| p99 | 1,790.4ms | 1,002.4ms | **21.1ms** |
| max | 1,828ms | 1,082ms | **45ms** |

**해석**: 마찬가지로 완전 해소(실패 0건). 애초에 이 프로파일이 "가벼운 부하"로 설계됐던 이유대로
다시 동작한다 — p50이 10ms대로, 원래 의도했던 "세부 튜닝 확인용 baseline" 역할을 되찾았다.

**남은 일**: 이 엔드포인트(`GET /api/rooms`)는 실질적으로 해결됐다. 다음은 (1) 스레드 풀
설정만 단독으로 올렸을 때의 효과를 분리 검증(N+1 없이 스레드 풀만), (2) 다른 엔드포인트(로그인,
`chatMessage` 소켓 이벤트 등) 측정, (3) 페이지네이션 미적용 등 남은 항목 처리.

이후 코드 수정 후 재측정 결과는 "Baseline #4" 형식으로 이 아래에 계속 추가한다.
